# 1.0.18 semantic request scheduling audit

The previous frontend submitted partial ASR updates with a minimum spacing of 450 ms. Each submission repeated the semantic prompt and dialogue context even when the speaker had not finished. Hiding duplicate answers after classification did not prevent those requests from consuming tokens.

One local scheduler now coalesces revisions, keeps neighbouring new transcript fragments together, deduplicates already submitted stable fragments and applies a configurable minimum interval between classification batches. The default is five seconds, including for existing profiles without the new setting; the setting is saved in the existing profile file and can be adjusted between two and thirty seconds. This is an event-driven queue, not a periodic API poll. No new transcript means no model request. A failed structured-output response can still cause the existing single repair retry within a batch.

ASR final events are the primary endpoint signal. Partial text can be classified after 1.2 seconds without changes and an approximately 800 ms pause in the question audio. Missing audio telemetry falls back to text stability. Energy is taken from captured audio, not the Windows output-volume slider. Online and video modes use system audio only; offline questions use the selected microphone only. Online candidate microphone speech stays in dialogue context and does not create semantic requests or control their pause condition. The existing candidate-speaking display lock remains separate.

The existing final-only option is retained. Manual input still bypasses semantic classification. Pending batches are cancelled on stop; a completed request from a stopped session cannot update the UI. Batched current transcripts are excluded from the historical context to avoid sending the same text twice. Previous questions and candidate replies remain available for reference resolution.

Validation before packaging: production frontend build passed; the scheduler, dialogue-context, question-stability, dual-channel integration and lifecycle suite passed (17 tests). The guide was dismissed, persisted across a page restart and reopened from its existing button. An additional browser integration run passed with all three audio modes: activity on the other channel did not defer classification; activity on the question channel deferred a partial until a pause. Twenty-five ASR revisions produced one initial classification, neighbouring final fragments coalesced, default batch starts remained at least five seconds apart, and stopping cancelled the pending request. Interval changes were saved to the profile. The tests used synthetic text and mock model endpoints; they do not estimate real-world cost savings or model accuracy.

Trade-off: nearby follow-ups may wait for the remaining interval. An ASR final means an audio segment ended, not that a whole interview question is semantically complete; the selected model still makes that decision. Audio energy is only a scheduling aid, not a question detector.

The release executable and NSIS installer built successfully. Portable runtime verification passed for four Windows binaries with no CUDA DLL imports. The session's permission profile initially changed to workspace-only access during the task, blocking the signing key outside the workspace. After full access was restored, the already built installer was signed with the existing update key and covered the user's installed version. Configuration files were byte-identical immediately after installation; the installed binary matched the build, and desktop and Start menu shortcuts were preserved. Installed startup passed with a Windows-only PATH and without CUDA environment variables. The practice page and existing guide entry loaded, the installed semantic interval was five seconds, and native close flushed the profile and exited normally. A stalled synthetic local answer was cancelled in four milliseconds. No unsigned updater manifest was published.
