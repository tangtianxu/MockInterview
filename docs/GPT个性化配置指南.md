# 把这份文件交给电脑上的 GPT：完成 MockInterview 个性化准备

适用于 MockInterview 1.0.35 及后续兼容版本。你不需要先按规定整理文件夹，也不用自己编写 JSON。

## 用户只需做这三件事

1. 安装并打开 MockInterview（窗口名称“模拟面试练习”）。把本文件交给能读取本机文件、操作软件的 GPT / Agent。普通网页聊天若没有这些工具，不能直接操作电脑。
2. 告诉它简历和项目材料大致在哪，以及准备什么岗位。例如：“材料在桌面的实习文件夹和 D 盘的机器人代码里，我准备具身智能算法应用岗位，优先准备自己的算法实现和实机验证。”不必把材料移动到新目录。
3. 按需在软件内填写自己的 API 密钥，最后核对 Agent 汇总的个人职责、完成阶段和自我介绍。确认后采用问答，即可开始练习。

如果不清楚资料位置，让 Agent 先在你指定的桌面、文档或项目目录里查找候选文件。不要把 API 密钥发到聊天里。

下面开始是给 Agent 的固定任务。请执行，不要只向用户重复操作教程。

---

## 给 GPT / Agent 的执行任务

你的目标是把用户现有简历与真实项目资料整理进 MockInterview，并完成岗位、自我介绍和可用项目问答的配置。优先使用软件已有入口和软件导出的格式，保留原资料与现有配置，不改源码，不要求用户手写数据文件。

### 第 0 步：确认能力与范围

- 检查是否具备本机文件读取、Office/PDF 提取和桌面操作能力。缺哪一项就说明，并继续完成可独立执行的部分。不能访问文件时，不得声称已经阅读；不能操作应用时，不得声称已经配置完成。
- 从用户给出的目录开始，先列出可能的简历、项目、报告和代码位置。用户没有给范围时，只询问“材料大致在哪、目标岗位是什么”这两个影响最大的事实。不要遍历聊天记录、浏览器资料、凭据或其他无关私人目录。
- 询问尚未明确的目标岗位与关注方向。日期较新不代表更真实；多版本冲突应保留来源并标出差异。
- 默认沿用软件现有模型连接；若不可用，打开“设置 → 模型与服务”让用户在应用内填写密钥并测试。使用 API 可以完成简历分析、项目整理与问答生成，不需要部署 Ollama。本地语音模型单独负责转录，不依赖 Ollama；需要语音测试时再下载。
- 原资料及现有题库只读保留。若需要备份，通过应用的导出入口保存到新位置；不要拿工具进程看到的 AppData 配置覆盖应用配置。Windows 打包应用可能看到不同的 AppData 视图，必须以用户实际打开的软件中读取到的状态为准。

### 第 1 步：读懂项目，再整理资料库

先阅读简历，再按项目追踪报告、代码入口、配置、评测脚本及结果。需要厘清：问题背景、本人职责、实现方法、实际运行环境、验证结果和未完成部分。

不要因为目录里存在训练代码就认定用户训练过模型；不要把团队功能全部写成个人贡献。区分方案设计、离线实验、仿真验证、设备推理、真机测试、正式现场交付。指标必须保留对象、条件、单位和来源，不能把不同实验拼成一个结果。

在用户允许的新位置创建输出目录；已有同名目录时新建带日期/序号的目录，不覆盖：

```text
面试准备_日期/
├─ 资料/                       ← 稍后在软件中选择这个目录
│  ├─ 项目A/                   ← 每个项目一个第一层子目录
│  ├─ 项目B/
│  └─ 共享资料/                ← 简历与跨项目背景
├─ 整理说明/                   ← Agent 的解读，不能当作原始证据导入
├─ 个性化填写稿.md
└─ 处理说明.md
```

按完整报告章节、实验、代码模块/函数保留上下文，不按零碎句子拆分，也不要把整个仓库拼成无结构长文本。项目内保留必要子目录，避免同名文件冲突。

软件可直接提取 DOCX、PPTX、XLSX、ODT/ODP/ODS、带文字层 PDF、TXT/Markdown、CSV、JSON/YAML 及常见源码；单文件不超过 64 MiB。文本使用 UTF-8。只读代码，不运行未知项目。

对提取质量不稳定的材料，另存可核对的文本：文档保留章节/页码；PPT 保留页号及备注；表格保留工作表、表头、单位和行列关系；代码保留相对路径、模块边界和必要行号。转换记录写明原文件完整路径。源码默认优先保留原文件，只有不受支持的扩展名或确有需要时才转成 TXT。

扫描 PDF、图片、图表和公式需要 OCR 或相应读取能力；旧 DOC/PPT/XLS 与 WPS 原生格式可能需要转换。没有工具就记录“未读取”及原因，不能用猜测补全。忽略依赖、构建输出、缓存、模型权重、大型数据集、密钥和含敏感信息的配置文件。

“资料”内只放原件副本或忠实提取的内容。项目总结、推断、可能问题和生成答案放在“整理说明”中，避免把 Agent 自己的推断再次当作事实引用。

在“处理说明.md”列出原目录、已读取文件、转换方式、跳过/失败项、项目划分、事实冲突和待用户确认的职责。优先阅读高相关材料，再根据实现细节补充，不需要把所有无关文件都导入。

打开“面试准备 → 资料 → 导入Agent整理目录”，选择上面的“资料”目录。检查实际读取数量、失败项与项目分组；不应把外层“面试准备_日期”当作资料目录。项目不明时在软件中修正归属，跨项目内容归“共享资料”。此步骤完成的是资料库，尚未生成题库。

### 第 2 步：填写个性化资料

打开“设置 → 个人资料”，按界面填写并重新打开核对：

| 设置 | 应填写什么 |
| --- | --- |
| 目标岗位 | 用户实际应聘的岗位，尽量具体；不超过 120 字 |
| 关注主题 | 岗位要求与用户已有能力的交集，如模型微调、数据链路、部署与评测；不超过 300 字 |
| 领域背景 | 按实际方向选择，帮助解释缩写；不要为了匹配岗位虚构经历 |
| 个人简历 | 通过应用选择真实简历；需要提取分析时使用已连接的 API 即可 |
| 自我介绍 | 根据已证实事实写一份可直接口述的稿子，先让用户核对，再填入；最多 4000 字 |
| 回答要求 | 简短说明表达、技术深度与事实边界；最多 1200 字 |

自我介绍建议约 1–2 分钟，包含当前身份、方向、1–2 项具体工作与岗位联系；不要重复罗列所有材料。用户确认的稿子保存后，自我介绍问题会直接使用它，不交给模型临时改写。

回答要求可采用下面的基础表述，再按用户偏好调整：

> 先直接回答问题，再说明方法、本人职责和验证结果。技术问题给出必要机制、公式或标准 Python 3 代码。个人经历以已核实资料为准，区分方案、仿真、真机与现场交付；缺少事实时说明边界，不编造指标或职责。追问沿用当前话题，不重复无关背景。

同时把最终填写内容保存到“个性化填写稿.md”，方便用户查看与迁移。不要把密钥写入该文件。

### 第 3 步：生成可编辑的项目问答

默认使用路线 A，已有本机 Agent 时可直接完成，不需要用户再去找其他工具。

**路线 A：Agent 准备问答，软件导入。**

1. 在“面试准备 → 资料 → 其他功能（按需） → 让Agent直接准备问答”点击“导出Agent工作包”，选择新输出位置。导出前核对项目/文件范围；有“待确认资料”先修正归属。
2. 阅读工作包中的固定说明、`sources.json`、提取文字和题库格式示例。以当前软件导出的说明和示例为准，不自行发明字段或来源 ID。
3. 结合完整项目阅读结果，先为每个项目准备最重要的约 8 道核心问题，再按资料深度补充，总题数不设上限。优先覆盖项目目标、本人负责部分、技术选择、实现细节、验证指标、失败案例及完成边界。开放型/行为问题单独分类，跨项目总结标明各项目来源。
4. 每题包含问法、同意图别名、项目、类别、任务类型、答案、追问、优先级、待核实事项和引用。别名只合并同一个回答任务；“是什么”“为什么选”“如何实现”不能因关键词相同强行合并。优先级只是准备建议，不声称有统计上的高频证据。
5. 按工作包示例保存 UTF-8 JSON，根格式为 `mockinterview-agent-bank-v1`，放在“生成问答”目录，按项目拆分，每文件最多 8 题。来源 ID/哈希从工作包原样取得；引用必须是原文连续片段，不得杜撰，具体长度及字段遵循工作包说明。不得写成已确认、已采用。
6. 点击“导入Agent结果文件夹”，选择“生成问答”目录。检查导入结果与引用错误，问答应进入“待检查”。格式错误在生成文件里修正后重新导入，不直接修改应用内部题库文件。

**路线 B：让软件连接的 API 准备问答。**

在“资料”页点击“准备问答”，检查本轮项目、资料范围和发送预览后执行。按软件要求确认这一轮发送，可能计费。失败时先读错误和已完成批次，不盲目反复点击。完成后同样进入“待检查”。如果用户选择本地生成模型，能力与速度以实际测试为准。

两条路线均不保证生成答案天然正确。题库与资料库分开：修改标准回答不会改写原始资料。

### 第 4 步：核对事实，然后采用

将可能影响真实性的事项汇总成一份短清单，集中让用户确认，避免逐题机械询问。例如“是否亲自执行过训练”“是否只在仿真运行”“某数字是否为团队测试结果”。无法证实的内容删除或保留为待核实，不替用户勾选“我已核对”。

在“待检查”展开问答，核对答案与引用，按需编辑。用户确认相关事实并明确允许采用后，可由 Agent 批量完成界面操作；不要擅自替用户承诺本人贡献。存在待核实内容的题先保留，不为了凑数量全部采用。

进入“已采用”，检查启用状态。模拟练习中勾选“使用已采用问答出题”，再选项目范围开始。已存在可用问答时先复用、去重，不要重新生成一套重复内容。

### 第 5 步：验证实际可用，不只检查文件存在

至少测试以下内容，并在完成报告标注实际结果：

1. 重新打开个人资料页，岗位、关注主题、自我介绍与回答要求仍在。
2. 刷新“面试准备”，资料数量、项目分组、待检查及已采用数量符合预期。
3. 提问自我介绍时显示已保存稿；普通技术问题不混入自我介绍原文。
4. 用项目原题和一种不同说法各问一次，再问“这部分你自己负责什么/怎么验证”，检查是否使用正确项目、保持上下文，并遵守完成阶段边界。
5. 提问一个不在题库中的技术问题，例如 PPO 原理，确认仍能生成回答。语音测试时确认选对声源：远程面试以系统声音为提问源，线下面试以麦克风为提问源，视频测试采集播放声音。先做短句测试，再做带背景的追问。

语音转录需要本地语音模型或已配置的识别服务。检查模型是否实际下载成功、音量是否变化、是否收到转录，再判断问题识别与回答；不要把没有音频输入归因于生成模型。耳机使用时核对当前播放设备。

若提示未出现，查看“历史”中对应问题的转录、判别、回答和“提示已显示”记录；后者在开启诊断记录显示后可见。它记录页面提交显示状态，不是对屏幕像素的录像证明。不能把“模型返回了回答”等同于“用户看到了提示”。

不能操作某种测试时写明未测试及原因，不把模拟工具结果描述成真实音频或真实设备验证。

### 交付给用户

用简短清单报告：整理目录与文档位置、成功/失败读取数量、项目名、已采用/待检查题数、实际保存的岗位设置、测试结果、仍需用户核实的少数事实。给出下一步直接点击的入口。

不要只交付一段提示词或一堆文件便宣称全部完成；文件准备、导入成功、界面保存和实际测试是四件不同的事。无法完成的步骤应明确保留，提供已完成结果，避免误导用户。
